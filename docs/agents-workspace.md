# Agents workspace implementation plan

**Status** Implemented and verified locally. This plan builds on the current working tree, including the Agent Inbox implementation documented in [the agent overhaul](agent-overhaul.md).

Replace the notebook’s **Agent Inbox** entry with **Agents**. The command center opens Main chat on a fresh visit. A direct link opens its target. The notebook panel and the command center share the selected conversation, drafts, messages and decision cards. Each side chat keeps its own Flue history and working context.

## What the user sees

| Destination | Contents | Primary interaction |
| --- | --- | --- |
| Main chat | The persistent assistant conversation, selected notebook context, and milestone updates from side chats | Continue the conversation or branch from a specific exchange |
| Needs attention | One row per unresolved question or decision, with its conversation, request and age | Open the exact event and review it in context |
| All activity | A chronological feed of work across chats, scheduled runs and connectors | Inspect grouped operations, sources, results or failures and jump to the owning timeline |
| Side chats | Recent objectives with titles, last activity and outstanding decision counts | Resume, create, rename or archive a conversation |
| Archived chats | Inactive objectives with their history and source links intact | Read, resolve outstanding work or restore |

Use a simple navigation column and a timeline with a composer. On small screens, navigation and the selected timeline occupy successive screens with ordinary Back behavior. Show run details on demand. Group tool calls under a disclosure such as “Checked your calendar · 4 operations.” Show the actual before/after diff, decision controls and execution receipt in sequence. Use the active theme’s tokens. Display the source, count, trigger or finding only when the application has evidence for it.

## Who owns each piece of state

**A workspace record outlives every session that references it.** Allocate a stable workspace ID when an action, proposal, question or milestone is created. Keep the proposed operation, relevant evidence, target revision and outcome in workspace storage. Reuse the existing domain record and ID wherever one already exists. Record references separately so zero, one or many chats can point to the same object. The originating session is provenance. Ending a run, clearing its model context, archiving a chat or dropping the last reference leaves the object and its history intact.

A new session can open a record by ID, inspect its current version and link it into another conversation. The human reviews the same versioned proposal from any authorized surface. If its source transcript is unavailable, the workspace record supplies the review context. Completion, rejection, supersession, an explicit business deadline or a stale target changes the record’s status. Its ID continues to resolve. Workspace execution and recording the outcome proceed independently of any optional Flue continuation.

**Workspace discovery.** Any chat in the same workspace can search active workspace records on demand and link an existing record. A conversation starts with its own history. Retrieving another conversation’s messages uses the explicit context-sharing flow in step 4.

| Owner | Durable responsibility |
| --- | --- |
| Flue conversation | Authored messages, ordered conversation history, tool calls, runtime signals and submission settlements. Keep the existing Main and side conversation identities. |
| Per-user `UserPlanner` | Side-chat directory and lifecycle, branch/report relationships, durable workspace action and proposal records, many-to-many chat references, human responses, effect receipts, delivery jobs and owner-scoped turn references. Its rebuildable indexes support search, activity and jumping to events. |
| Browser | Selected view and item in the URL, composer drafts per chat, keyboard focus and originating-tab edits. React Query caches planner records. Flue streams the open conversation. |

**The global attention queue is a query.** The current inbox already filters pending records and computes its count from the same predicate. Keep that implementation and the human decision endpoint. Preserve the existing adapter for legacy time proposals, including its decision, version, replacement and undo behavior. A transcript card holds the item ID. Opening it fetches the current record. The historical tool result remains a record of what the agent originally proposed. [Inbox domain](../apps/api/src/core/agent-inbox.ts) · [Decision routes](../apps/api/src/routes/agent-inbox.ts) · [Legacy Review migration](../apps/api/drizzle/0011_agent_inbox.sql)

**Example.** A side chat proposes moving a Thursday study block. In one planner transaction, persist the proposal and its timeline reference. Needs attention now returns one row. Opening the row lands on the diff, even after hundreds of newer messages. Approving sends the reviewed item ID and version to the existing decision handler. A local edit commits with its decision. An external change can show “Approved · awaiting provider” while its delivery is pending. The row leaves Needs attention when the human decision is settled. The timeline and All activity continue to show the operation’s outcome. When a continuation is appropriate, an alarm delivers the outcome to the originating workflow with an idempotent signal. Its delivery status is tracked independently of the decision and effect. Opening the same card from Main, a push notification or another tab shows the same outcome.

## Implementation order

### 1. Ship the workspace and contextual queue as the first slice

- Add canonical routes under `/app/agents` for Main, side chats, attention, activity and archive. Extend the existing navigation and history handling. Split conversation selection from opening the notebook panel, which are currently coupled in `selectChat`. Extract the timeline, composer and subscription logic from `chatbar.tsx` for use in either shell. Preserve independent drafts, pending submissions, attachments and reply targets while switching surfaces. Attach selected notebook text/task only on a notebook-originated send or explicit attachment. [Chat state](../apps/web/client/chats.ts) · [Chat panel](../apps/web/client/chatbar.tsx) · [Navigation](../apps/web/client/main.tsx)
- Render Needs attention as a paginated list of links. Keep the badge driven by `needsAction`. Reading a row leaves it actionable. Include pending provider questions. Keep informational notices, completed requests and already-approved provider jobs in activity. Move approve, dismiss/reject, request changes and answer controls to the contextual card. Existing `?inbox=<id>`, notification, workspace-command and revised-proposal links resolve through the same item locator. Preserve time-change undo.
- In the first additive migration, add a typed locator for a decision’s public display chat and event and a durable Main fallback event for items without an addressable public origin. Keep the private resume address on the existing workflow record. Select one canonical review location even when several timelines reference the item. Attach scheduled, connector and legacy items without a public originating chat to Main as labeled application events. Continue delivering their answers to the original workflow. Fetch the item by ID first. Use a generation-scoped message/tool anchor and bounded older-history pages to bring the surrounding exchange into view. If the event predates reliable linkage, show its durable card and available source context. Never jump silently to the latest message. [Inbox projection](../apps/api/src/core/agent-inbox.ts) · [Transcript](../apps/web/client/chat-transcript.tsx) · [Chat API](../apps/api/src/app.ts)
- Fetch per-chat pending reply targets from the planner. Today the client derives them from tool outputs inside its 200-message observation window. Bind an answer to the selected item ID and version. Keep the normal message composer available when several decisions are pending. After a decision, invalidate the item, per-chat targets, queue, badges and relevant planner views. Refresh other tabs on focus or via a scoped invalidation broadcast.
- Include device-only confirmations in the global view. When the originating tab has an actual preview ready, register one canonical pending item keyed to the verified submission and `showWorkspace` call. Bind it to the initiating tab’s opaque claim. The queue links to that preview and identifies when the original tab is required. Validate the human decision before that tab applies it, then reconcile its terminal receipt. Expired previews or interrupted application surface “Unavailable” or “Check outcome” with an explicit reissue path. Immediate navigation commands emit receipts directly. [Device journal](../apps/web/client/device-delivery.ts) · [Receipt verification](../apps/api/src/agents/device-receipt.ts)

**Exit test.** Produce a proposal in side chat A, end the run, archive A, and make its transcript unavailable. Start a fresh chat B, link the proposal by workspace ID, review its saved diff, and approve it. Verify one edit, one decision and one durable outcome even if a Flue continuation fails. Revisit the same ID in another tab. Also test a pending proposal with zero chat references. Repeat with an old proposal, a provider question and an originating-device preview.

### 2. Build the shared timeline and All activity

- Extend the event storage and decision locator shipped in step 1 to cover all activity sources. Add per-conversation projection checkpoints. Give events a stable source identity, display chat, occurrence time and typed references to the submission, message, tool call, item and affected entity where applicable. Store display-safe labels and relationships. Derive current decision status from the canonical item.
- Write planner events in the transaction that publishes or changes the underlying item. Emit distinct events for proposal, revision, approval, effect success/failure and undo. Use the same path for background sources. An update to yesterday’s proposal must appear at the time of today’s decision. Include successful reads and runs with no inbox item.
- For Flue activity, schedule durable reconciliation on admission for user sends and internal dispatches. A bounded worker reads committed history and settlements by cursor through the owner-scoped router. Use the existing planner alarm’s earliest-due scheduling, yield between batches and periodically reconcile missed admissions. Live observation improves latency. Record progress even when all browser tabs are closed. On a history reset, rebuild the transcript projection for the new generation. Preserve workspace action records and their outcomes through the reset. Preserve source order inside a chat. Globally sort by event occurrence time with a stable tie-break and a snapshot watermark for paging. Delayed imports appear on refresh.
- Backfill public Main and registered side chats in small pages, plus existing inbox items and recorded domain outcomes. Preserve available provenance for private historical runs. Historical steps without durable evidence stay absent. The UI can mark search/activity coverage as “Indexing earlier conversations” during backfill. [Flue routing and conversation history](https://flueframework.com/docs/guide/routing/) · [Planner alarm](../apps/api/src/user-planner.ts)

**Exit test.** Finish a routine with the browser closed and a side-chat turn that only reads data. Both appear on reopening All activity. Replaying a projection batch adds zero duplicate events. An admitted, failed or aborted run displays its actual terminal state.

### 3. Branch, return and archive

- Extend the side-chat directory with archive time, title updates and branch provenance. Migrate existing side chats as active and keep their UUIDs. Main remains permanent. A side chat’s archive state controls discovery. Pending requests remain globally discoverable, existing continuations can settle, and users can restore the chat before starting new work.
- Add **Continue in side chat** on a Main exchange. Show a suggested title and an editable context preview from selected messages. Allow copying the context or regenerating the preview before creation. Only the user’s confirmation starts the branch. An agent suggestion opens the same flow.
- Register the child, selected source anchors and a frozen starter brief transactionally. Deliver the starter as a typed context signal with an idempotent outbox operation. Quoted instructions carry no new write authority. A separately authored user instruction follows the ordinary user-turn path. Show “Starting” until Flue admits it and retry the same operation after failure. Start the side timeline with a source quote and **View original conversation**. Main shows a link back to the new objective. Carry factual context into the branch. Pending decisions travel as links to their existing IDs.
- **Exit test.** Double-click Continue, lose the response, and reopen the app. Find exactly one side chat with one starter and reciprocal links. Its first answer has access to the approved excerpt. Archive and restore it without breaking a pending decision or citation. [Side-chat routes](../apps/api/src/routes/chats.ts) · [Chat identity](../apps/api/src/agents/chat-identity.ts)

### 4. Add explicit cross-chat text search and references

- Support three entry points: an `@conversation` chip in either composer, **Search main context** from a side chat, and **Search side chats** from Main. A user can search across active side chats without knowing a title. A selected conversation narrows the scope. Archived chats are available through an explicit filter or selection. Keep entity and conversation mentions distinguishable.
- Use SQLite FTS5 inside the existing per-user Durable Object for lexical search. Feed it the finalized, user-visible text projection from step 2. Strip transport prefixes and implicit notebook metadata. Exclude raw tool payloads, hidden signals, credentials and provider form answers. Return bounded excerpts with chat title, timestamp and a source-message link. Revalidate selected evidence against its source generation. Render exactly which conversations and messages were consulted. SQLite-backed Durable Objects support FTS5. [Cloudflare SQLite storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- Extend user-turn admission with structured reference IDs or a user-selected search scope. A plain-language request such as “search my side chats for the Hawaii deposit” can open an explicit scoped search through the same send flow. Resolve ambiguous scope with a picker. Bind the approved scope to owner, destination chat and stable admission key. Freeze the inputs for network retries and reject changed payloads under that key. Resolve search permissions for the executing submission on the server. Share source IDs and excerpts as evidence. A future turn can use excerpts already shared in its own history; searching for additional material requires its own scope.
- Add typed Hono/OpenAPI operations for conversation search and bounded source retrieval. Expose the scoped reads to Copilot via the existing MCP catalog. Provide workspace-wide discovery of active work in every chat. Return the record’s own reviewable fields through the planner API. A reference to an originating conversation gives the agent an address; access to additional transcript text follows the user-selected scope. [Public admission](../apps/api/src/app.ts) · [Planner MCP transport](../apps/api/src/mcp/connection.ts) · [Inbox routes](../apps/api/src/routes/agent-inbox.ts)
- **Exit test.** Seed synthetic Main and side chats with overlapping terms and one private detail each. Verify Main → named side chat, Main → all authorized side chats and side chat → Main, including an older result outside the latest 200 messages. Verify citations, revoked/unavailable sources, excluded fields, account switching and that a later unreferenced turn cannot retrieve fresh material from the other conversation.

### 5. Let a side chat report a milestone and wake Main

- Implement `reportMilestoneToMain` as a **native Flue tool** mounted with `useTool` on eligible side-chat turns. Inputs are a short headline, outcome and optional typed links to evidence, artifacts or an existing decision. Derive the owner and source from the runtime and fix the destination to that owner’s Main chat. Expose **Report back to Main** as a user action backed by the same domain operation. Mount the automatic tool for consequential completed outcomes, such as an accepted itinerary or a finished analysis, and make the source activity visible. [Copilot](../apps/api/src/agents/copilot.ts) · [Native tool example](../apps/api/src/agents/workspace-command.ts) · [Flue tools](https://flueframework.com/docs/guide/tools/)
- Persist the immutable report, source and destination timeline links, and a delivery job in one planner transaction. Derive a stable occurrence key from a canonical completion receipt or a durable milestone ID for conversational work. Retain tool-call and user-action retry keys as aliases. Re-reporting the same milestone returns its existing card. A new outcome gets a new occurrence.
- The existing alarm delivers a trusted `side_milestone` signal with `dispatch(Copilot, { id: mainIdentity, idempotencyKey: reportId, ... })`, persists the admission receipt and reconciles settlement. In Main render **Update from Plan Hawaii trip** with **View conversation** and a verified artifact link when one exists. The report is readable while delivery is pending or if the model response fails. Record delivery and response status separately. The side tool returns promptly after the durable enqueue. [Existing dispatch pattern](../apps/api/src/agents/inbox-resume.ts) · [Flue durability](https://flueframework.com/docs/guide/durability/)
- Treat the report as information. A report alone can acknowledge or summarize; it confers no planner-write, connector, device or re-report authority. Flue can join a delivery to a busy response. Persist the report card immediately and defer the wake when necessary to isolate it from user-authorized work. Implement and test a per-Main admission boundary across browser and internal senders before enabling automatic wakes. A “check idle, then send” race is insufficient. Correlate a joined delivery using its settlement and host submission when present. [Flue events](https://flueframework.com/docs/reference/events/)
- **Exit test.** Retry the tool and user action for the same milestone, crash after admission, and deliver while Main has an authorized edit in flight. Expect one report card, one logical wake, the original edit’s correct outcome, and no extra writes or report loop.

## Keyboard, migration and release checks

Use the existing shortcut registry and command palette. The default `g a` opens the full Agents workspace within the notebook's shared navigation. The default `g q` opens Quick chat beside the notebook. Keep the notebook panel button and `/agent` and `/side` commands. Within Agents normal mode, offer `g m` for Main, `g i` for attention, `]d` / `[d` for unresolved decisions and `za` for the focused operation group. Preserve the notebook’s existing `g m` for next month. Add **Find conversation** and **Branch from selection** to the existing palette; offer scoped Ctrl+P and leader-b bindings without overriding custom bindings, text input, IME or native browser shortcuts elsewhere. Validate keyboard focus after navigating to an older card and on Back. [Current keymap](../apps/web/client/preferences.ts) · [Keyboard routing](../apps/web/client/vim.ts)

Land additive schema and API changes first. Generate OpenAPI, browser types and MCP artifacts using the repository scripts. Cut over the UI after existing IDs and old links resolve. Extend the existing chat, inbox, device, connector and migration suites; add an isolated two-tab Chrome flow for approvals, branching, references and report-back. Run both workspace typechecks, test suites, production builds and `npm run openapi:check`. Exercise the new model tools separately against synthetic conversations and inspect both the tool trace and persisted outcome.

**Delivery sequence.** Ship the command center and contextual review first. Build out chronological activity and branch/archive next. The searchable projection and scoped tool reads precede cross-chat retrieval. Enable automatic milestone wakes after retry and busy-Main tests pass. Each slice can be accepted independently.


## Verification record

The full workspace suite passed 157 API tests and 118 web tests. Both production builds, both typechecks and the OpenAPI drift check passed. An independent reviewer exercised the built app in desktop and mobile Chrome and used live Flue conversations with synthetic data.

- A fresh chat searched, retrieved and linked a pending proposal from an archived chat. The workspace-only regression exercised the same operation without any source transcript, including concurrent approvals and a single resulting edit.
- A side chat searched explicitly referenced Main messages, branched with a verified source link, and used the native milestone tool to wake Main. A busy Main turn and the milestone acknowledgement settled separately. Repeated delivery produced one report.
- Two browser tabs saw the same decision. Only the originating tab could authorize and apply its device preview. A saved notebook-page link opened its actual content.
- The existing development planner upgraded in place through migrations 0012 and 0013. Tests cover partially initialized workspace tables and an already-applied directory migration.
