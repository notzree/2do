# 2do agent overhaul

Implementation plan and coordination record. The baseline for the inventory and review is `33ca71b`.

Keep Flue for conversations and execution. Build one Agent Inbox per planner, shared by main chat, side chats, connectors and scheduled runs. Agents express changes as typed diffs. The approval policy can authorize a change from an explicit request or a scoped standing permission. The inbox holds changes that need review, questions and informational updates. A user should be able to say “move my lab to Thursday,” resolve an ambiguity, approve the exact change, and see the same result in Week as if they had used the inspector. They should also be able to close 2do and receive a requested reminder. Those are two independent release tests.

## Where the Agent Inbox lives

**Recommendation.** Give the inbox its own domain module, API and web panel inside the existing per-user `UserPlanner` Durable Object. Cloudflare recommends choosing an object boundary around the entity whose state must be coordinated. Each object has its own transactional storage. Here the entity is one person's planner. Accepting “move lab to 4 pm” must commit the reviewed schedule, approval receipt, updated inbox state and any change to the reminder timer together. The existing time Review already updates a task and its proposal in the same local transaction. A separate inbox object would require durable messages, deduplication and reconciliation across two databases on that path. [Cloudflare object boundaries](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/) · [Cloudflare storage guarantees](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/) · [Current Review transaction](../apps/api/src/core/review.ts)

Flue's conversation object owns the transcript and execution. It publishes an inbox item through an owner-scoped operation and keeps a reference to its ID. Google connection objects own grants and provider sync. Network calls run after the local commit. If notification delivery or live fan-out measurably delays planner edits or alarms, extract a per-user delivery service fed by a transactional outbox. Measure planner write latency, alarm lateness, inbox traffic and delivery backlog before introducing that boundary. A shared team inbox spanning multiple planners would also justify revisiting ownership.

## 1. Build the full-stack Agent Inbox

Evolve the existing Review panel and sidebar entry into **Agent Inbox**. Chat, an inbox deep link and a device notification should all open the same item. The inbox stays available when its originating conversation is closed.

| Item | What the person sees | Effect of ignoring it |
| --- | --- | --- |
| Proposal | “Move Physics Lab on Thursday from 2–3 pm to 4–5 pm.” Show before and after, why, which records change, and any Google Calendar effect. Offer Approve, Reject or Request changes. | The accepted plan stays as it was. The proposal can expire or become stale. |
| Question | “Which lab did you mean?” Show Physics and Chemistry with dates. Accept a choice or a typed answer. | Only the workflow that needs this answer waits. Other chats and scheduled jobs continue. |
| Notification | “Your 4 pm Physics Lab starts in 15 minutes.” Show the relevant time, source and optional task link. | Delivery completes when the notice is published to the inbox. Reading, replying and dismissing are optional. |

Each item has a stable ID, source and source event key, optional originating conversation, creation time, and read/archive state. Keep decision or answer status in its own domain record. Deduplicate publication by source and occurrence. Index by creation order and pending status. Existing time proposals keep their IDs, original decision history, duplicate aliases and undo checks. Backfill canonical proposals into the inbox idempotently and adapt existing Review callers to the same decision records. Verify a pending proposal created before deployment can still be decided exactly once.

**API and UI.** Provide paginated list, detail, unread and needs-action counts, and idempotent read/archive operations. Human answer/decision endpoints take an item ID and version. Producer operations publish typed items with a trusted owner. Evolve `review-inbox.tsx`, `sidebar.tsx` and `workspace-panels.ts` with All, Needs action and Updates views. Use the existing React Query client for refresh on mutation, focus and bounded polling while visible. Counts refresh even when chat is closed. Opening an actionable item can mark it read while it remains under Needs action. Keep pending decisions discoverable until resolved. Render the same diff or question in chat by item ID. ## 2. Apply one approval policy to agent changes

Route every agent write through one server-side policy evaluator. Flue interprets the request and proposes a typed change. The planner resolves the targets, computes the diff and evaluates it against the user's permissions. The inbox can ship with manual review first. Auto-approval can be enabled later through the same write path.

**What a rule covers.** A rule describes the origin of the request, the operations and resources it covers, and the effects the user permits. Derive the affected fields, number of records, destination, reversibility and downstream effects from the command and actual state. A plugin or connector declares its operation and effects through the action contract. It can use the same policy as any existing capability. Bind a direct request to its authenticated turn and resolved targets. A scheduled job needs a matching standing permission to make an automatic edit. Connector content supplies evidence.

| Decision | When it applies | User experience |
| --- | --- | --- |
| Apply | The requested change is clear, permitted and entirely within an auto-approval rule. | Commit the change, return a receipt and offer Undo when supported. |
| Clarify | The intended target or outcome is ambiguous. | Ask for the missing information, then evaluate the resolved change once. |
| Request review | The change is allowed but its effects exceed the rule, or the user chose “Always ask.” | Show the full diff and wait for the user's decision. |
| Block | The user lacks access or the domain forbids the operation. | Explain the constraint. Inbox approval cannot supply a missing provider grant. |

For example, a user could allow explicitly requested, reversible edits to their personal planner. Renaming a task and reordering notebook entries could both qualify. The same rename on a published calendar event also changes the provider copy, so a local-only permission sends it to review. This decision follows from the resolved effects even when the same MCP tool handles both renames. Evaluate a grouped change as a whole.

Store policy preferences per user and allow scoped rules to be inspected, changed or revoked. An explicit review preference wins over an overlapping automatic rule. If no rule covers a valid write, create a proposal. Re-evaluate permissions and versions at commit, record the authorization source and applicable rule with the diff, and return the original receipt on replay.

For device-local edits, the browser applies the approved diff against the originating tab's current version and returns a receipt. The UI must distinguish a committed approval from an effect still waiting on a browser or provider.

1. **Generate a reviewable change.** Declare an execution policy alongside each action contract consumed by the MCP generator. Build the Copilot catalog from reads, typed change requests and interaction tools. Replace today's direct model writes, including task creation/update/deletion, page edits, dependency edits, plugin workflows and carryover, with a path through the approval policy. Enforce the policy at invocation as well as discovery. Keep authenticated human decision endpoints outside the model's tool set. Reuse the same Zod shapes and domain commands as the UI. Add a contract test that fails on an unclassified capability or an agent mutation that bypasses this policy. Roll the new catalog and diff handlers out together per capability. [MCP handler](../apps/api/src/mcp/server.ts) · [Copilot instructions to update](../apps/api/src/agents/copilot.ts)
2. **Compute the diff from authoritative values.** For planner changes the server resolves a typed command against current state. For device-local changes the originating browser supplies the preview and version, then checks both when applying it. Persist an immutable proposal revision containing typed operations, target IDs, base values/versions, proposed values and external effects. The same stored operations drive both the rendered diff and execution. Show creations, removals, changed fields and cascades. For a batch such as moving a lab and its prep session, show both changes and apply the approved local group atomically. Split independently selectable changes into explicit groups. “Make it 4:30 instead” creates a replacement revision for review.
3. **For changes requiring review, bind approval to what the human saw.** Accept a button or an unambiguous typed response to the displayed item and revision through an authenticated human route. A model interpretation can locate a proposal or ask which one. Approval evidence comes from the user's bound response. On approval, reload records and validate affected fields and domain rules. Preserve unrelated edits where the command permits. A conflicting change invalidates the diff and requires a new preview. Repeated identical decisions return the original receipt. A competing decision receives the stored outcome or a conflict. Preserve the existing guarded undo for eligible time moves.
4. **Commit and resume.** Atomically store the local edits, authorization receipt, any applicable inbox update and durable requests for follow-up work. Resume the originating Flue conversation with a stable dispatch key if it needs the result. A planned external write has a displayed destination and its own delivery state, such as queued, applied, failed or conflicted. The executor uses the approved payload, checks the current grant and provider version, and records the provider outcome. Scheduled reminders already authorized by a rule can publish notifications when due.

**Acceptance.** Use table-driven tests to apply one rule across task, notebook and plugin operations. Run the same typed change under a direct request, a scheduled run with and without standing permission, and “Always ask.” Verify that ambiguous targets elicit a question, a mixed local/external batch goes to review as a whole, and a revoked provider grant blocks execution. Test paraphrases in the Copilot evals against the same resulting diff and decision. Retry a committed edit from a second tab and verify one receipt. Change a target before approval and verify that a stale grouped diff cannot partially apply. [Review tests](../apps/api/test/review.test.ts) · [Copilot evals](../apps/api/evals/copilot.mjs)

## 5. Deliver task-based notifications while 2do is closed

Use the notification item from the first inbox release. A rule, connector or Flue run can publish a relevant fact and settle immediately. For example, a calendar sync can surface “Physics Lab moved from 2 pm to 4 pm” with a source link. If the agent also wants to move a prep session, publish a linked proposal for that distinct decision. A notice can appear on its own, without a composer, response deadline or approval controls. Start scheduled delivery alongside connector work. Explicit reminders can ship before any external connector. Implement reminder rules and occurrences in the planner database, with API and MCP operations to create, list, edit, cancel, snooze and dismiss. Support an absolute instant and a task-relative offset first. Add user-enabled rules for due tasks, blocked work and a morning brief. Persist the IANA zone, local delivery time for date-only tasks, quiet hours, channel and enabled state. An undated task needs a chosen time or a matching rule before it can generate a timed reminder.

1. **Schedule on change.** Reconcile affected occurrences in the same planner transaction as task creation, rescheduling, completion, deletion, import, or rule changes. Track the rule version and the relevant due/schedule fields. An unrelated title edit updates display text without creating another reminder. Index pending work by UTC `dueAt`. Backfill existing open tasks when a rule is enabled, in resumable batches. Recompute calendar-day occurrences from the local zone across DST and on zone changes.
2. **Wake and recheck.** Extend `UserPlanner.nextDue()` and `alarm()` with a bounded due-work batch. On wake, reread the task, rule and delivery window. Suppress obsolete work, defer quiet-hour delivery, coalesce related suggestions, and expire stale nudges after downtime. Re-arm for the next occurrence or retry. Exercise the existing classification, carryover and effect queues under the same alarm.
3. **Use the model when there is a decision.** A 15-minute reminder needs a template and a timer. A brief or “this prerequisite puts Friday at risk” can use Flue. Persist a job and its owner routing key, then dispatch a typed server signal with a stable `idempotencyKey`. The planner object ID is opaque. Capture the authenticated routing identity when enabling the feature. Initially scope background runs to reading and publishing inbox items, with a bounded number of model calls. Once standing permissions ship, submit any proposed background edit to the same policy evaluator with its scheduled origin. Publish their results to Agent Inbox with the originating task and rule. Choose a notification for information, a question for a missing input, or a proposal for a recommended change. Recheck inputs before publication. If a synthesis run fails, an explicit timed reminder still fires.
4. **Deliver and let the user act.** Commit the notice and delivery outbox together using a unique occurrence key. Show unread notices in Agent Inbox. Offer a task link and context-appropriate optional actions such as Snooze or Discuss. A notification creates no pending interaction, and a device receipt never acts as an answer. Add opt-in Web Push, per-device subscriptions, a service worker, and a deep link to that same notice. Recheck authorization and relevance before sending. Retry transient failures with backoff, retire expired subscriptions, and use the same notification tag on retry. Provider acceptance and user interaction are distinct receipts. A denied push permission still leaves the notice available in the app. [Web Push API](https://www.w3.org/TR/push-api/)

**Acceptance.** “Remind me 15 minutes before my lab.” Move it from 2 pm to 4 pm, close every 2do tab, and receive one device notification for the 3:45 occurrence. Tap it, snooze ten minutes, then mark the task done before the snooze expires. Verify no later notice. Repeat with duplicate alarms, a worker restart, a DST boundary, denied notification permission and a device offline past the delivery window. For a morning brief, a quiet day produces no interruption, and a blocked task can produce one informational notice with zero pending actions. A user who selects Discuss can continue in chat.
